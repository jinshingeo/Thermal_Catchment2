## 4. 핵심 발견 — 소프트웨어 버그와 구조적 제약

### 4-1. `Tgmaps_v1.py` 버그 (치명적, 수정 완료)

UMEP 플러그인 내 `SOLWEIGpython/Tgmaps_v1.py` 9행에 다음과 같은 버그가 있었음:

```python
id = np.unique(lc_grid)              # 토지피복 고유값(7개 안팎) 산출
id = lc_grid[lc_grid <= 7].astype(int)   # 버그: 방금 구한 id를 그리드 전체로 덮어씀
```

이로 인해 반복문(`for i in id:`)이 원래 의도한 7회가 아니라 **타일 전체 픽셀 수(680만개)만큼**
반복되며, 매 반복마다 배열 전체 비교연산을 5회씩 수행 — 사실상 O(N²) 연산으로 서울 규모
타일에서는 무한루프에 가까웠음(수정 전 타일1은 8시간 넘게 이 단계에서 멈춰 있었음).

**수정**: `id = id[id <= 7].astype(int)` (9행)로 교체 — 이후 해당 단계는 1분 이내로 통과.
성동구 파일럿처럼 작은 그리드에서는 이 버그가 체감될 만큼 느리지 않아 발견되지 않았던
것으로 추정됨.

### 4-2. SOLWEIG 동시실행 불가 (구조적 제약, 우회 완료)

`solweig_algorithm.py`의 `self.temp_dir`이 프로세스별로 고유하지 않고 플러그인 설치
경로 하위의 **고정된 공유 경로**로 지정되어 있음. SOLWEIG는 SVF 압축파일(svfs.zip)에서
`svf.tif`를 이 공유 temp 폴더에 압축해제한 뒤 읽는데, 2개 이상의 SOLWEIG 프로세스를
동시에 실행하면 서로의 압축해제 파일을 덮어써 "확장자 불일치/zip 손상" 오류가 발생함
(실제로 타일0·2 최초 시도에서 이 오류로 실패).

**결론**: SVF는 병렬 가능(3-way까지 확인)하지만, **SOLWEIG는 반드시 순차 실행**해야 함.
이것이 전체 파이프라인의 구조적 병목.

## 6. 향후 운용 논의를 위한 시사점

1. **SOLWEIG 순차 제약이 최대 병목**: SVF처럼 병렬화만 가능하다면(temp_dir을 프로세스별
   고유 경로로 고치면 됨) SOLWEIG도 3-way 병렬 시 약 3.5시간으로 단축 가능 — 이 경우
   총 소요시간이 18~19시간 → 약 12시간대로 줄어들 것으로 예상.
2. **시나리오(날짜/시간대 조합) 추가 시 선형 증가**: 현재는 "폭염 7일 평균 06~19시" 1개
   시나리오 기준. CLAUDE.md의 "방식 2"(시간대별 diurnal profile, 여러 날짜)로 확장할
   경우 시나리오 수만큼 위 총계가 곱해짐 — 예: 5개 시나리오 시 약 90~95시간(순차) 소요.
3. **메모리는 병목이 아님**: 타일당 30~48GB로, 124GB 서버 기준 3개까지는 안전하게 병렬
   가능함이 이미 확인됨(SVF에서). 서버 자원 자체는 여유 있고, 소프트웨어 구조(SOLWEIG의
   공유 temp 경로)가 유일한 제약.
4. **1m 해상도(성동구 파일럿 규모)는 이 문제와 무관**: Tgmaps_v1 버그는 그리드 크기에
   비례해 증폭되므로, 서울 전체처럼 큰 타일에서만 치명적으로 드러남. 작은 지역 재실행
   시에는 이 기록이 크게 중요하지 않을 수 있음.

## 7. 타일링 방법론 — 버퍼 기반 분할과 이론적 타당성

### 7-1. 왜 버퍼가 필요한가

SVF·SOLWEIG는 각 픽셀에서 여러 방향으로 광선을 쏴서 주변 건물이 하늘/햇빛을 가리는지
확인하는 방식으로 계산한다. 타일을 버퍼 없이 딱 붙여 자르면, 타일 경계 근처 픽셀 입장
에서 실제 그림자를 드리우는 옆 건물이 인접 타일 데이터에 있어 보이지 않는 상황이 발생
하여 "타일 경계 아티팩트"(경계 근처만 부정확하게 밝게 계산됨)가 생긴다.

### 7-2. 버퍼 크기 산정 (삼각함수 근거)

건물 높이 H, 태양 고도각 θ일 때 그림자의 최대 수평거리:

```
d = H / tan(θ)
```

대표 건물높이 H=100m, 분석시간대(06~19시) 최저 태양고도 θ≈6°를 적용:

```python
import math
H, theta = 100, 6  # m, deg
buffer_m = H / math.tan(math.radians(theta))  # ≈ 950m
```

5m 해상도 기준 950m = 190px를 버퍼 폭으로 채택.

### 7-3. 실제 타일링 코드 (`17b_tile_seoul_5m_v2_8split.py`)

```python
RES = 5.0
BUF_PX = 190      # 950m
N_TILES = 8

core_w = width // N_TILES   # 서울 전체 폭(7410px) 8등분 → 926px

tile_ranges = []
for i in range(N_TILES):
    core_start = i * core_w
    core_end = (i + 1) * core_w if i < N_TILES - 1 else width
    buf_start = max(0, core_start - BUF_PX)   # 왼쪽 버퍼(도메인 끝이면 0)
    buf_end   = min(width, core_end + BUF_PX) # 오른쪽 버퍼(도메인 끝이면 width)
    tile_ranges.append((core_start, core_end, buf_start, buf_end))
```

산출된 `tile_ranges.json` 중 타일1 예시:

```
core: [926 : 1852]        ← 최종적으로 사용할 영역
buffered: [736 : 2042]    ← 계산은 이 범위 전체로 수행(좌우 190px씩 여유)
```

### 7-4. 계산 후 처리 — 버퍼는 계산 후 반드시 폐기해야 함

SVF/SOLWEIG는 버퍼 포함 영역 전체로 계산되므로(현재 `Tmrt_*.tif`는 아직 버퍼 포함
상태), 최종 모자이크 전에 코어 영역만 크롭해야 이론적으로 완전하다:

```python
# 모자이크 단계에서 수행 예정 (아직 미실행)
core_offset = core_start - buf_start
tmrt_core = tmrt_tile[:, core_offset : core_offset + (core_end - core_start)]
```

### 7-5. 한계 — 100m 가정이 깨지는 경우

건물 높이 100m 가정은 롯데월드타워(555m)나 북한산(836m) 같은 초고층/고지형에는 맞지
않는다. 이런 구조물이 타일 경계 950m 이내에 위치한다면 버퍼가 부족해 경계 아티팩트가
남을 수 있음 — 타일 경계선 8개가 실제로 이런 지물 근처를 지나는지 지도 확인이 필요
(미확인 상태, 후속 작업으로 남겨둠).

## 8. 1m 해상도로 서울 전체 확장 시 실현 가능성 검토

**결론부터: 현재 서버(124GB RAM)·현재 버퍼 타일링 방식으로는 1m 해상도 서울 전체
SOLWEIG는 구조적으로 불가능하다.** 아래는 실제로 시도해서 실패한 것이 아니라, 5m에서
확보한 실측 처리율을 근거로 계산한 추정치다(성동구 단독 1m은 데이터 구축·SOLWEIG 실행
모두 별도로 검증되어 있으며 이 문제와 무관).

### 8-1. 단순 선형 시간 추정 (버퍼 비용 미포함)

```python
total_time_min = 597          # 5m 8타일 SOLWEIG 실측 합계(분)
total_core_px  = 7410*6063    # 5m 전체 코어 픽셀
rate = total_time_min / (total_core_px/1e6)   # 13.29분/백만px

w1m, h1m = 37054, 30317       # 1m 그리드(같은 bbox)
px1m = w1m*h1m                 # 1123.4M px

est_min = px1m/1e6 * rate      # ≈ 14,928분 = 248.8시간 = 10.4일
```

→ 버퍼 오버헤드를 전혀 고려하지 않아도 **SOLWEIG만 약 10.4일** 소요 추정(SVF 별도).

### 8-2. 결정적 문제 — 버퍼가 메모리 예산 자체를 초과함

950m 버퍼는 해상도와 무관하게 물리량(그림자 도달거리)으로 고정된 값이므로, 1m에서는
**950픽셀**이 된다(5m에서는 190픽셀이었음). 메모리 예산 내에서 타일이 가질 수 있는
최대 폭을 계산하면:

```python
mem_budget = 100e9   # 여유있게 100GB 예산
patches, arrays, bytes_per = 153, 3, 8   # shadowmat/vegshadowmat/vbshmat, float64
h1m = 30317

max_total_width_1m = mem_budget / (h1m * patches * arrays * bytes_per)
# ≈ 898px  ← 이게 버퍼+코어 합쳐서 한 타일이 가질 수 있는 최대 폭

buf_px_1m = 950
core_remaining = max_total_width_1m - buf_px_1m*2
# ≈ 898 - 1900 = -1002px  ← 음수!
```

**버퍼 하나(양쪽 합 1,900px)만으로 이미 메모리 예산이 허용하는 최대 타일 폭(898px)을
초과한다.** 즉 이론적으로 타당한 버퍼를 유지하면서 메모리에 들어가는 타일을 만드는 것
자체가 불가능하다 — "코어 영역이 존재하는 타일"을 단 하나도 만들 수 없다는 뜻.

### 8-3. 정리

| 구분 | 5m (현재) | 1m (검토) |
|---|---|---|
| 필요 버퍼 | 190px | 950px (5배, 물리량 고정이라 해상도와 무관) |
| 메모리예산 내 최대 타일 폭 | 약 1,300px | 약 898px |
| 버퍼가 타일에서 차지하는 비중 | 약 15~30% | **100% 이상 (코어 공간 없음)** |
| SOLWEIG 단순 선형 추정 | 9시간 57분(실측) | 약 10.4일 (버퍼 비용 제외, 과소추정) |

**결론**: 1m 해상도는 시간이 오래 걸리는 정도가 아니라, 현재 버퍼 기반 타일링 방식과
서버 메모리 조합에서는 **애초에 유효한 타일을 구성할 수 없는 구조적 한계**에 부딪힘.
극복하려면 (a) 버퍼를 줄여 경계 아티팩트를 감수하거나, (b) 서버 메모리를 큰 폭으로
증설하거나(수백 GB~TB급), (c) 알고리즘을 타일 경계를 넘나드는 방식으로 재설계해야 함
— 셋 다 현재 일정(SCI 8월 투고) 내에서는 비현실적임.

## 9. 모자이크·시각화·링크할당 소요시간 (2026-07-16, 후속 작업)

### 9-1. 타일 모자이크 (버퍼 크롭 후 병합)

8타일 → 서울 전체 단일 래스터(14시간대+평균) 병합. 서버에서 실행, 별도 시간

### 9-2. 링크 단위 Tmrt 할당 (Colaninno et al. 2024 버퍼+zonal mean 방식)
